EuPago Production Issue Summary
===============================

Context
-------
- Application: Palmanhac (Next.js, `/en/checkout`), running behind the Cloudflare tunnel `https://human-managed-won-chemistry.trycloudflare.com`.
- Environment variables (`.env` / `.env.local`):
  * `EUPAGO_API_BASE="https://clientes.eupago.pt"`
  * `EUPAGO_API_KEY="e9c2-89a9-20c2-39c9-2a6b"`
  * `EUPAGO_CARD_RETURN_URL="https://human-managed-won-chemistry.trycloudflare.com/orders"`
  * `EUPAGO_WEBHOOK_SHARED_SECRET="UN9Bojg4nNTUXGDxAWyKkCF9im4Odkrf"`
- Checkout server-side logs (see `eupago-errors-5.txt`) show that:
  * Multibanco requests reach `https://clientes.eupago.pt/clientes/rest_api/multibanco/create` with a URL-encoded form body (`id`, `valor`, `descricao`, `email`, `currency`, `apiKey` injected automatically) and return `{"sucesso":false,"estado":-10,"resposta":"Os dados inseridos não são válidos"}`.
  * MB WAY and Card requests target `https://clientes.eupago.pt/api/v1.02/{mbway|creditcard}/create` with the documented snake_case JSON fields (`value`, `currency`, `description`, `customer_email`, `customer_name`, `alias`/`return_url`, `locale`) and include all header variants (`ApiKey`, `Authorization: ApiKey …`, `X-Api-Key`). EuPago responds with HTTP 401 and `{ code: "APIKEY_MISSING" }`.

Steps Already Taken
-------------------
1. **Verified API key handling:** The adapter now injects `ApiKey`, `Authorization`, and `X-Api-Key` headers for all `/api/v1.02/*` endpoints and ensures `apiKey` only appears in the body for the legacy `/clientes/rest_api/*` calls. The headers are visible (with the key redacted) inside `logs/payments.log`.
2. **Validated payload shape:** Card and MB WAY payloads only contain the fields EuPago’s documentation lists (see `txt/prd/task8.2_prd.txt`). Multibanco bodies are URL-encoded with `valor` (string such as `"39.95"`) plus the optional `currency` field, no nested objects.
3. **CLI reproduction:** Using `curl` with the same API key produces the exact same errors; sample commands and responses are recorded in `eupago-test-requests.txt`. This proves the failing behavior is on EuPago’s side rather than the app.
4. **Removed host rewrites:** Requests now go exactly to `https://clientes.eupago.pt` (no auto-switching to `https://eupago.pt`), so we are not hitting the marketing site anymore.

Observed Errors
---------------
1. **Card & MB WAY (`/api/v1.02/.../create`):**
   - Response: `{"transactionStatus":"Rejected","code":"AMOUNT_MISSING","text":"Amount was not available in the request"}` when using `value` in the form body, even though the key is accepted (HTTP 200).
   - When testing against the sandbox base with the same key, EuPago returns `{"code":"APIKEY_INVALID"}`, which suggests this key is a *production* key, not a sandbox key.
   - When hitting the production base, EuPago sometimes still responds with `{"code":"APIKEY_MISSING"}`, which indicates the production account may not have these channels active.
2. **Multibanco (`/clientes/rest_api/multibanco/create`):**
   - Response: `{"sucesso":false,"estado":-10,"resposta":"Os dados inseridos não são válidos"}`. This is EuPago’s generic “invalid data” response and usually means the backoffice has not enabled the requested entity/reference generation for the supplied API key.

What Still Needs EuPago’s Help
------------------------------
We have reached the point where the Palmanhac application is sending the correct payloads, but EuPago refuses them. To move forward, please contact EuPago support and request the following checks on the backoffice (they can do this from the Integrations › API or Channels screens):

1. **Confirm the API key is active for all three channels:**
   - Multibanco references (legacy REST endpoint)
   - MB WAY (v1.02 API)
   - Credit Card (v1.02 API)
   If any of these aren’t enabled, support needs to associate the API key with the respective services.

2. **Clarify the expected amount field:**
   - Card & MB WAY endpoints are documented to accept `value` (string/decimal). We’re sending `value=39.95` (and we’ve tried `amount`, `valor`, integers, commas). Support should confirm whether the production tenant expects `amount` instead, or if there is a currency/decimal configuration tied to the merchant profile.
   - Ask them to provide a working `curl` example for this specific key so we can mirror it exactly.

3. **Validate Multibanco template:**
   - The response `estado: -10 / Os dados inseridos não são válidos` typically means the backoffice template for Multibanco references is misconfigured or the account is still in review.
   - Support can inspect the merchant’s Multibanco “Entidade” and “Subentidade” and ensure the `apiKey` is mapped to a valid contract. They might need to regenerate or reassign the key.

4. **Check IP or domain restrictions:**
   - If EuPago enforces allowed origins, make sure `human-managed-won-chemistry.trycloudflare.com` (and the eventual production domain) is whitelisted, otherwise the API may reject requests even when the payload is correct.

5. **Webhook / return URL validation:**
   - Confirm that `https://human-managed-won-chemistry.trycloudflare.com/orders` is registered as an allowed return URL for credit card payments.

Expected Outcome After EuPago Changes
-------------------------------------
Once EuPago enables the channels / fixes the account configuration:
1. `createCard` should return `paymentUrl` + `transactionId`; the frontend will redirect to the hosted checkout, and the webhook will mark the order as PAID.
2. `createMBWay` should return `transactionId` + `statusUrl`; the UI will start polling `/api/payments/eupago/status`, and webhook callbacks will finalize the order.
3. `createMultibanco` should respond with `{ entity, reference, amount, expiresAt }`, letting the checkout display the reference block; webhook notifications will later mark the order as PAID.

Until EuPago resolves the API-side rejection, the Palmanhac checkout must keep showing an error message after submission. All application-level bugs identified earlier have been fixed; the remaining blocker is purely on the provider’s side.
